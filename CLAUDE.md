# PSEMS Backend — Context for Claude Code

## What this is
Backend for PSEMS (Project Scoring, Evaluation & Management System) — a CO3554 university project (5 credits) that must launch as a **real single-department faculty pilot by end of September 2026**. Full spec is in `docs/` (read `PSEMS_Comprehensive_Specification_v2.docx` for full detail — roles, 12-step CPI lifecycle, DB schema, ML endpoints; `PSEMS_Delivery_Roadmap.md` for the week-by-week build plan).

## Repo layout reality
This is one of **four separate repos** (polyrepo, not monorepo):
- `psems-backend` (this repo) — Node.js 20 / Express / TypeScript / Prisma / PostgreSQL+pgvector / Redis
- `psems-frontend` — React 18 / TypeScript / Vite / Tailwind
- `psems-ml-service` — Python 3.12 / FastAPI / scikit-learn / sentence-transformers
- `psems-infra` — docker-compose.yml for local Postgres+pgvector and Redis (shared by backend and ml-service)

Architecture is a **modular monolith**, not microservices: this backend is ONE deployable service with internal modules (auth, students, courses, groups, ideas, selection, allocation, evaluations, scoring, headjudge, scheduling, marks, analytics, notifications, files). Only the ML layer is a separate service, deliberately decoupled so the platform works even if ML is down.

Before touching this repo, bring up shared infra from the sibling `psems-infra` repo: `docker compose up -d` (Postgres+pgvector on 5432, Redis on 6379). `.env.example` in this repo has the connection strings.

## Timeline reality — read before making architectural decisions
Starting from zero on 2026-07-05, solo developer, ~12.5 weeks to a real pilot launch (not just a demo). The original spec's Gantt chart assumed 8 months — we've compressed to single-department pilot scope (matches the spec's own "Phase 1: single department" future roadmap) rather than cutting features. Non-negotiables regardless of time pressure: evaluator score isolation before Head Judge review, forced first-login password change + bcrypt + short-lived JWTs, RBAC enforced at both middleware AND service layer, audit logging on all writes, anonymized historical data before ML use. See the roadmap doc for the exact cut-list priority if something has to give.

**New feature proposed 2026-07-25 (not in original spec, user's own idea): presentation-day timer.** During a scheduled presentation, whoever runs the room (an assigned evaluator or the Head Judge) starts/pauses/resumes/stops a stopwatch; only the final elapsed duration gets saved once, so it's a shared fact visible to everyone scoring that session and to the Head Judge in review — not a live-synced clock across browsers (unnecessary complexity for a pilot). Needs: a nullable `presentationDurationSeconds` (or similar) on `EvaluationSession`, one save endpoint (coordinator/assigned evaluator/HJ can set it), surfaced read-only in `ReviewPage`. Time-management scoring itself needs no new mechanism — the coordinator can already add a "Time Management" rubric criterion via existing Evaluation Config; this feature only makes the actual duration knowable, doesn't auto-penalize. See `psems-frontend/CLAUDE.md` for the matching UI piece. Full gap list (this + everything else found in testing) consolidated in `docs/E2E_TEST_GUIDE.md` section 4.2.

**Spec-compliance audit against Steps 7–10, 2026-07-25 — 5 more real gaps found (code-read, not yet exercised in a live test):**
1. **(Highest priority — blocks multi-stage submissions) Submission deadline is hardcoded to the single `PROPOSAL_SUBMISSION` phase for every submission-required stage**, regardless of which stage (`files.service.ts` `submitProposal`, the `cpiTimeline.findUnique` call hardcodes `phase: CpiPhase.PROPOSAL_SUBMISSION`). A real config with Proposal/Mid/Final Demo/Report each needing their own submission window can't work — they'd all share one deadline. Needs either a per-stage deadline field (e.g. `EvaluationStage.submissionWindowStart/End`) or a rework of how stage submissions map to timeline phases.
2. **`EvaluationStage.evaluatorsRequired` is stored but never enforced.** `scoring.service.ts` `refreshSessionReadiness` completes a session once every *currently assigned* `stageEvaluator` has scored — it never reads `evaluatorsRequired`. Setting it to any number currently does nothing.
3. **Allocation map never surfaces unassigned supervisor-posted ideas**, only unmatched groups (`allocation.service.ts` `getAllocationMap`). Spec explicitly calls for resolving both in Supervisor-Led mode.
4. **`scheduleSession` never calls `notify()`.** Spec says students/evaluators get notified of their confirmed schedule; currently nobody is notified when a session's time is set.
5. **No mode-branching in allocation logic at all** — Supervisor-Led and Coordinator-Managed use identical `generateAllocations`/`overrideAllocation`/`finalizeAllocations`. Coordinator-Managed's spec'd "reviews all pairings and confirms or reassigns" isn't a distinct per-pairing workflow, just the same generic override. Functionally equivalent outcome, doesn't match spec'd UX — lower priority than 1–4.

Also confirmed by design, not bugs: submission deadlines are soft (late accepted + flagged, per `files.service.ts`'s own comment); evaluation config is fully locked once any submission exists (can't add/reweight stages mid-way); no file-type restriction on uploads (any type up to 20MB, fine for presentations).

**Reclassified 2026-07-25, user wants these fixed (were previously logged as accepted tradeoffs):**
- **Password re-ask on forced first-login change.** Skip `currentPassword` verification in `authService.changePassword` specifically when `user.forcePasswordChange === true` — that call *is* the mandatory reset, the user just proved they know the password by logging in with it seconds ago. Keep the check for any later voluntary change.
- **No scheduling-conflict detection.** `scheduleSession` should check the proposed start/end against every other session already scheduled for any evaluator assigned to this one (across all their groups/stages), and ideally against their submitted availability too. Recommend: surface as a clear warning naming the conflicting session, not a silent hard block — coordinator should still be able to override deliberately, just never find out about a double-booking by accident.
- **No venue/room/link field on `EvaluationSession`.** Add an optional free-text `location: String?` (not a URL — room number, video link, or blank are all valid, a link isn't always available). Include it in the schedule-confirmation notification (which also needs to be added — see the notify() gap above) sent to students and the supervisor.
- **No "overdue" signal on a session.** A session whose scheduled time passed with no scores in still just reads `SCHEDULED`, identical to one that hasn't happened yet. Add a derived `isOverdue` (scheduledEnd < now && status === SCHEDULED) either in the API response or purely frontend-side — no new persisted field required.

**Correctness bug found during end-to-end pilot test (2026-07-24) — touches the isolation/integrity rule, higher priority than the notify() gap below.** `scoring.service.ts` `submitScores` only rejects writes when `session.status === FINALIZED` (line ~31). It does NOT reject writes once status is `AWAITING_HEAD_JUDGE`. That means an evaluator can keep resubmitting/changing their scores after both evaluators have already scored and the session is sitting with the Head Judge — silently, without going through the `CORRECTION_REQUESTED` flow that `headjudge.service.ts` `requestCorrection` exists specifically to gate. The session status model clearly intends scoring to be locked between "complete" (`AWAITING_HEAD_JUDGE`) and an explicit Head Judge correction request — `submitScores` needs the same guard extended to reject (or at minimum, only accept from) any status other than `SCHEDULED` or `CORRECTION_REQUESTED` (and for `CORRECTION_REQUESTED`, scoped to the specific evaluator whose correction was requested, not any evaluator). Frontend also doesn't disable the score inputs at `AWAITING_HEAD_JUDGE` (`LecturerSessionsPage.tsx` only checks `status === 'FINALIZED'`) — fix both together. **Fix before pilot** — this is adjacent to the evaluator-isolation non-negotiable even though isolation itself (who can *see* scores) tested correctly.

**Bug found during end-to-end pilot test (2026-07-23):** group-member invites never call `notify()` (`groups.service.ts`), unlike supervisor invites/allocation/HJ actions which do. An invited student currently has no way to learn they were invited to a group except being told the group's UUID out of band. Add a notification on group invite creation, same pattern as `inviteSupervisor` in `courses.service.ts`. Paired with a frontend fix (pending-invites list) — see `psems-frontend/CLAUDE.md`.

**Process note (2026-07-21):** `psems-frontend` was 6 weeks behind and has now fully caught up (Weeks 1–6 all clickable in a browser, not just API-tested). Going forward, build each backend week's frontend screen(s) *alongside* it, not in a later catch-up block — that gap was the single biggest risk to the project for two weeks running.

## Current phase

**Restructure Wave 3 COMPLETE as of 2026-08-16 (uncommitted).** Availability grid, timetable builder and the multi-segment presentation timer. One migration (`availability_grid_and_timer_segments`), hand-written so the 4 live `evaluator_availability` rows were converted into the new grid rather than dropped - verified after the run: 2 templates, 4 slots, 4 AVAILABLE cells, all four lecturers intact. **84 tests / 15 suites green**, tsc + lint clean.

- **Availability is a grid, not free-text ranges.** `AvailabilityTemplate` (date window = columns) + `AvailabilityTemplateSlot` (named day-parts = rows) + `PanelAvailability` (AVAILABLE / TENTATIVE / UNAVAILABLE per cell). Two people offering "Tuesday afternoon" and "14:00-16:00 Tue" were previously incomparable, so the old model could not build a timetable at all.
- **`EvaluatorAvailability` is dropped.** Availability now keys on **`Lecturer` + `courseInstanceId`**, not `CpiEvaluator` - a supervisor outside the evaluator pool used to get a hard 403 with nowhere to record a slot.
- **Policy says who is *expected*, not who is *permitted*.** `availabilityRequiredFrom` drives the coordinator's "still to answer" list; submission itself is open to any evaluator, accepted supervisor, or seated panelist. Refusing a supervisor's "I'm away that week" is the exact bug being fixed, so the permit is deliberately wider than the policy.
- **Bulk replace-all `PUT /availability`** - the submitted set is the complete answer, so omitting a cell clears it. That is the withdraw path the old write-once model never had. Plus `GET /availability/mine` (read-back, also absent before).
- **Conflict detection rewritten against `SessionPanelist`.** It read `StageEvaluator` - the table Wave 1 superseded - so it was clearing slots the real panel could not make. Five kinds now: `PANELIST_DOUBLE_BOOKED` (across CPIs, since a lecturer cannot be in two rooms at once on any course), `GROUP_DOUBLE_BOOKED`, `ROOM_DOUBLE_BOOKED`, `OUTSIDE_AVAILABILITY`, `REQUIRED_PANELIST_MISSING`. All advisory - never a block.
- **Silence is not a refusal.** `OUTSIDE_AVAILABILITY` fires only for lecturers who actually filled the grid in. Flagging non-respondents would warn on every session of every course where availability is optional, and a warning that always fires is one nobody reads.
- **`GET /sessions/:id/alternative-slots`** intersects the submitted availability of everyone the stage *requires* (optional walk-ins never constrain a move) and ranks by least disturbance: firmly free over tentative, emptier slot over one needing a reshuffle. Naming who is missing was only half an answer.
- **Scheduling opens with `AVAILABILITY_SUBMISSION` and never closes with it** - the gate moved from the route into the service. A timetable is edited *most* after the window shuts (someone drops out, a room changes), and the route gate made that a hard 403. Bulk `PUT /sessions/schedule` lays out a block in one call.
- **`SESSION_RESCHEDULED`** is now its own notification with locale-formatted times; a move is not the same event as a first booking, and both used to arrive as `SESSION_SCHEDULED` with raw `toISOString()`.
- **`listSessions` widened** - students see their own group's sessions (403 before, the one thing a timetable exists to tell them), supervisors see every group they supervise rather than only those they hold a seat on. `GET /schedule-sheet` is the printable handout (group blocks with `No | Index Number | Name`, date, time range, venue); **coordinator-only**, because it names every student on every group and distributing it is the department's call.
- **Multi-segment timer.** `TimerSegmentTemplate` per stage (authored in the evaluation config, patchable at `PUT /stages/:id/timer-segments` outside the submission lock) is **copied** onto `SessionTimerSegment` on first use, so editing the template never rewrites a session that already ran. Actions widen to `start | pause | next | previous | stop | reset`.
- **Nothing advances on reaching a target.** Passing it starts counting the overrun; the evaluator presses Next when the group actually finishes. An auto-switch at the target would make overrun impossible to record - the one thing the feature exists to capture. `timeliness` is computed at close with a **proportional tolerance** (10% of target, capped at 15s): a flat 15s grace would be a third of a 40-second intro. Overridable per segment (`timelinessManual`), because a deliberate early finish is not an under-run.
- **`GET /sessions/:id/timer`** is deliberately light - the standalone window polls it about once a second and must not drag the session list across the wire each time. The timer's phase gate also moved into the service so a session running slightly outside the window does not 403 on every control press.
- `EvaluationSession.allocatedMinutes` lets a timetable be laid out from a slot length before any times are fixed.

- **Pooled marks.** `COORDINATOR_DECIDES` panelists are averaged into ONE contribution weighted by `EvaluationStage.pooledSharePercent`, capped by `pooledScorerLimit` — so a crowd cannot outvote the formal panel by number. Every change writes a `PooledShareDecision` with a **mandatory reason** (the weighting is chosen with scores visible — accepted risk, see the plan).
