# PSEMS Backend — Context for Claude Code


## Student provisioning: `year` dropped, `studentId` renamed to `studentIndex` (2026-08-23)

`tsc` + lint + `jest` clean — **135 tests / 17 suites**. Migration `20260823120000_drop_student_year` written and applied.

- **`Student.year` is gone.** It was written once at provisioning and read by nothing: no query filtered on it, no endpoint returned it (`grep "year: true"` → zero), no screen showed it. It was also wrong within twelve months, because a student advances and nothing updated the column. **`batch` is the durable key** — fixed for life, and what actually decides course visibility. Year of study is derivable from batch plus the current date if it is ever wanted.
- **The CSV column `studentId` is now `studentIndex`.** The value is the university index number, and calling it an id invited confusion with a database key. **`studentIndex`, `indexNumber` and the original `studentId` are all accepted**, so sheets the faculty office already prepared keep loading — covered by its own test.
- **The database column stays `studentId`.** Renaming it would touch every query that joins on it, the roster and the mark sheet, for no behavioural gain. The meaning is documented on the model instead.
- Header is now `email,fullName,studentIndex,registrationNumber,batch,department`.


## Search, coordinator demotion, and the supervisor's interest list (2026-08-25)

`tsc` + lint + `jest` clean — **142 tests / 18 suites**.

- **People search matched nothing, in every role.** `searchProfiles` queried `userProfile`, so anyone who had never opened Edit my profile did not exist to the directory or the search box. Production had **11 users and 0 profile rows** — so it matched nobody, always. It searches `user` now, left-joining the profile, and email was added to the searchable fields because that is what people remember about a colleague.
- **`POST /users/:id/revoke-coordinator`** undoes an accidental promotion. Refused with a 409 while they still coordinate a course, because the course's ownership and every phase gate hang off that role.
- **Promotion locked a lecturer out of everything they supervised.** The data was never lost — `listLecturerCpis` reads the `Lecturer` row and the `cpi_supervisors` junction, not `User.role` — but the frontend's `/lecturer` route was gated to `LECTURER` alone and the coordinator rail had no link to it. Fixed on the frontend; no backend change.
- **A student idea now flags itself as `SEEKING_SUPERVISOR` when posted**, unless it is awaiting coordinator approval or interest is disabled. It previously needed a second, separate button, so ideas sat unseen and supervisors saw an empty list.
- **`POST /selection/accept-interest`** lets a supervisor award their idea to one of the interested groups, with no formal selection from the group. Several groups usually want the same project and the choice is the supervisor's. The older route (group selects, supervisor confirms) still exists for `selectionConfirmedBy` and Coordinator-managed courses.
- **`getSelectionState`'s supervisor branch returns `interestInMyIdeas`**, each carrying `placedOn` when that group already has a project — otherwise the screen offers to take a group that is already spoken for.
- **A revived interest now counts against the course's cap.** Withdrawal is soft, and re-expressing cleared `withdrawnAt` without re-checking the cap, so withdraw-one-take-another-revive-the-first put a group over its limit.

## What this is
Backend for PSEMS (Project Scoring, Evaluation & Management System) — a CO3554 university project (5 credits) that must launch as a **real single-department faculty pilot by end of September 2026**. Full spec is in `docs/` (read `PSEMS_Comprehensive_Specification_v2.docx` for full detail — roles, 12-step CPI lifecycle, DB schema, ML endpoints; `PSEMS_Delivery_Roadmap.md` for the week-by-week build plan).

## Repo layout reality
This is one of **four separate repos** (polyrepo, not monorepo):
- `psems-backend` (this repo) — Node.js 20 / Express / TypeScript / Prisma / PostgreSQL+pgvector / Redis
- `psems-frontend` — React 18 / TypeScript / Vite / Tailwind
- `psems-ml-service` — Python 3.12 / FastAPI / scikit-learn / sentence-transformers
- `psems-infra` — docker-compose.yml for local Postgres+pgvector and Redis (shared by backend and ml-service)

Architecture is a **modular monolith**, not microservices: this backend is ONE deployable service with internal modules (auth, students, courses, groups, ideas, selection, allocation, evaluations, scoring, headjudge, scheduling, marks, analytics, notifications, files). Only the ML layer is a separate service, deliberately decoupled so the platform works even if ML is down.

Before touching this repo, bring up shared infra from the sibling `psems-infra` repo: `docker compose up -d` (Postgres+pgvector on 5432, Redis on 6379). `.env.example` in this repo has the connection strings.

## How the developer wants to work

Default to explaining reasoning and letting them drive implementation, rather than silently generating large chunks of code. **New feature proposed 2026-07-25 (not in original spec, user's own idea): presentation-day timer.** During a scheduled presentation, whoever runs the room (an assigned evaluator or the Head Judge) starts/pauses/resumes/stops a stopwatch; only the final elapsed duration gets saved once, so it's a shared fact visible to everyone scoring that session and to the Head Judge in review — not a live-synced clock across browsers (unnecessary complexity for a pilot). Needs: a nullable `presentationDurationSeconds` (or similar) on `EvaluationSession`, one save endpoint (coordinator/assigned evaluator/HJ can set it), surfaced read-only in `ReviewPage`. Time-management scoring itself needs no new mechanism — the coordinator can already add a "Time Management" rubric criterion via existing Evaluation Config; this feature only makes the actual duration knowable, doesn't auto-penalize. See `psems-frontend/CLAUDE.md` for the matching UI piece. Full gap list (this + everything else found in testing) consolidated in `docs/E2E_TEST_GUIDE.md` section 4.2.

**Spec-compliance audit against Steps 7–10, 2026-07-25 — 5 more real gaps found (code-read, not yet exercised in a live test):**
1. **(Highest priority — blocks multi-stage submissions) Submission deadline is hardcoded to the single `PROPOSAL_SUBMISSION` phase for every submission-required stage**, regardless of which stage (`files.service.ts` `submitProposal`, the `cpiTimeline.findUnique` call hardcodes `phase: CpiPhase.PROPOSAL_SUBMISSION`). A real config with Proposal/Mid/Final Demo/Report each needing their own submission window can't work — they'd all share one deadline. Needs either a per-stage deadline field (e.g. `EvaluationStage.submissionWindowStart/End`) or a rework of how stage submissions map to timeline phases.
2. **`EvaluationStage.evaluatorsRequired` is stored but never enforced.** `scoring.service.ts` `refreshSessionReadiness` completes a session once every *currently assigned* `stageEvaluator` has scored — it never reads `evaluatorsRequired`. Setting it to any number currently does nothing.
3. **Allocation map never surfaces unassigned supervisor-posted ideas**, only unmatched groups (`allocation.service.ts` `getAllocationMap`). Spec explicitly calls for resolving both in Supervisor-Led mode.
4. **`scheduleSession` never calls `notify()`.** Spec says students/evaluators get notified of their confirmed schedule; currently nobody is notified when a session's time is set.
5. **No mode-branching in allocation logic at all** — Supervisor-Led and Coordinator-Managed use identical `generateAllocations`/`overrideAllocation`/`finalizeAllocations`. Coordinator-Managed's spec'd "reviews all pairings and confirms or reassigns" isn't a distinct per-pairing workflow, just the same generic override. Functionally equivalent outcome, doesn't match spec'd UX — lower priority than 1–4.

Also confirmed by design, not bugs: submission deadlines are soft (late accepted + flagged, per `files.service.ts`'s own comment); evaluation config is fully locked once any submission exists (can't add/reweight stages mid-way); no file-type restriction on uploads (any type up to 20MB, fine for presentations).

**Reclassified 2026-07-25, user wants these fixed (were previously logged as accepted tradeoffs):**
- **Password re-ask on forced first-login change.** Skip `currentPassword` verification in `authService.changePassword` specifically when `user.forcePasswordChange === true` — that call *is* the mandatory reset, the user just proved they know the password by logging in with it seconds ago. Keep the check for any later voluntary change.
- **No scheduling-conflict detection.** `scheduleSession` should check the proposed start/end against every other session already scheduled for any evaluator assigned to this one (across all their groups/stages), and ideally against their submitted availability too. Recommend: surface as a clear warning naming the conflicting session, not a silent hard block — coordinator should still be able to override deliberately, just never find out about a double-booking by accident.
- **No venue/room/link field on `EvaluationSession`.** Add an optional free-text `location: String?` (not a URL — room number, video link, or blank are all valid, a link isn't always available). Include it in the schedule-confirmation notification (which also needs to be added — see the notify() gap above) sent to students and the supervisor.
- **No "overdue" signal on a session.** A session whose scheduled time passed with no scores in still just reads `SCHEDULED`, identical to one that hasn't happened yet. Add a derived `isOverdue` (scheduledEnd < now && status === SCHEDULED) either in the API response or purely frontend-side — no new persisted field required.

**Correctness bug found during end-to-end pilot test (2026-07-24) — touches the isolation/integrity rule, higher priority than the notify() gap below.** `scoring.service.ts` `submitScores` only rejects writes when `session.status === FINALIZED` (line ~31). It does NOT reject writes once status is `AWAITING_HEAD_JUDGE`. That means an evaluator can keep resubmitting/changing their scores after both evaluators have already scored and the session is sitting with the Head Judge — silently, without going through the `CORRECTION_REQUESTED` flow that `headjudge.service.ts` `requestCorrection` exists specifically to gate. The session status model clearly intends scoring to be locked between "complete" (`AWAITING_HEAD_JUDGE`) and an explicit Head Judge correction request — `submitScores` needs the same guard extended to reject (or at minimum, only accept from) any status other than `SCHEDULED` or `CORRECTION_REQUESTED` (and for `CORRECTION_REQUESTED`, scoped to the specific evaluator whose correction was requested, not any evaluator). Frontend also doesn't disable the score inputs at `AWAITING_HEAD_JUDGE` (`LecturerSessionsPage.tsx` only checks `status === 'FINALIZED'`) — fix both together. **Fix before pilot** — this is adjacent to the evaluator-isolation non-negotiable even though isolation itself (who can *see* scores) tested correctly.

**Bug found during end-to-end pilot test (2026-07-23):** group-member invites never call `notify()` (`groups.service.ts`), unlike supervisor invites/allocation/HJ actions which do. An invited student currently has no way to learn they were invited to a group except being told the group's UUID out of band. Add a notification on group invite creation, same pattern as `inviteSupervisor` in `courses.service.ts`. Paired with a frontend fix (pending-invites list) — see `psems-frontend/CLAUDE.md`.

**Process note (2026-07-21):** `psems-frontend` was 6 weeks behind and has now fully caught up (Weeks 1–6 all clickable in a browser, not just API-tested). Going forward, build each backend week's frontend screen(s) *alongside* it, not in a later catch-up block — that gap was the single biggest risk to the project for two weeks running.

## Current phase

**Hosted, and a Super Admin tier, as of 2026-08-23 (committed, not pushed).** **134 tests / 17 suites green**, tsc + lint clean. PSEMS now runs at `psems-foe-usj.tech` (SPA on Vercel) and `api.psems-foe-usj.tech` (this API on Render free), against Supabase Postgres and Supabase Storage. Redis is Render Key Value. **No ML service is deployed** — nothing here calls it; `ML_SERVICE_URL` is declared and read by no module.

**The database was publicly readable and writable, and is the most important thing on this page.** Supabase publishes the `public` schema over PostgREST, reachable with the publishable key, which ships in browsers by design. Tables created by Prisma inherit grants for `anon`/`authenticated` and carry no row-level policy. Verified against the live database: an anonymous request read bcrypt password hashes out of `users`, and a `PATCH` was accepted — any row, including a role change to SUPER_ADMIN. Closed by `restrict_public_schema_access`: RLS on every table plus revoked grants and default privileges, so future tables are not exposed as they are created. The owning role bypasses RLS, so the application is untouched. **Every new migration must enable RLS on the tables it creates** — the lockdown could only cover tables that existed when it ran; `password_reset_requests` does this.

- **The refresh cookie was the deployment's one real blocker.** Its attributes were written out at each call site and omitted entirely from `clearCookie`, so logout never matched the cookie it meant to remove. One `refreshCookieOptions` now covers login, refresh and logout. `SameSite` is `strict` by default and `COOKIE_SAMESITE=none` exists for a deployment split across unrelated registrable domains — which is why the SPA and API share `psems-foe-usj.tech` rather than sitting on `*.vercel.app` and `*.onrender.com`, hosts the Public Suffix List makes cross-site on purpose. `maxAge` is deliberately absent from the shared object: `clearCookie` merges it over its own epoch expiry and would re-issue the cookie instead of clearing it.
- **`/auth/refresh` returns the whole session**, matching login. The access token lives in memory, so a reload has only the cookie to rebuild from; returning just a token left the client with no user and nothing to route on. `refreshSession` already loaded the user, so this cost nothing.
- **`SUPER_ADMIN` is real and deliberately not nested above `SYSTEM_ADMIN`.** It was one line in the enum that nothing checked. It now creates System Admins, suspends and reinstates any account, resets any password, deletes an account **only when nothing references it**, reads the audit log and works the password-reset queue. It holds **none** of the course powers — a Super Admin gets 403 on `/lecturers/pending` and `/students/bulk-provision`, and a System Admin gets 403 on every `/super-admin` route. Both directions are tested. It also cannot act on its own account, so the last Super Admin cannot lock themselves out.
- **Suspension, not deletion, is the answer for a person.** Marks, scores and audit rows reference users, so removing a participant would take that history. Suspension needs a written reason, blocks login *and* refresh — so a session in progress dies within one access-token lifetime — and is reversible. Deletion is refused once anything points at the account.
- **A locked-out account can ask for help.** `POST /auth/password-reset-request` is unauthenticated by necessity and answers identically whether or not the address exists, so it cannot be used to discover accounts. A **partial unique index** allows one PENDING request per address, because the endpoint cannot require a session and would otherwise be a way to fill a table. A request for an unknown address is kept, not dropped — a mistyped address should be visible. Resetting the account closes its request.
- **Rate limiting existed nowhere.** `express-rate-limit` on login (10 per 15 min, failures only, so a shared campus address is not locked out by its own successes) and on registration and reset requests (5/hour). **Not constructed at all under test** — its memory store's cleanup timer stops Jest exiting.
- **CORS reflected any origin**; it now reads `CORS_ORIGINS`, trimming trailing slashes because an `Origin` header never carries one and a stray slash fails every request with an opaque error. `trust proxy` is set, since the host terminates TLS.
- **The seed refuses to run when `NODE_ENV=production`.** Its four passwords are committed to a public repository, so one misdirected `DATABASE_URL` would have created a System Admin whose password anyone can read. A deployment gets its first account from `npm run admin:create`.
- **`admin:create` and `superadmin:create`** share one implementation and differ only in role. No route mints either tier, so these are the only way the first account exists and the way back in when everyone is locked out. They are safe to commit: they need the database credentials to run and are not reachable over HTTP, so they grant nothing that holding those credentials does not already grant.
- **An uploaded file name was interpolated into the storage key.** It is a label, not a path; separators are stripped.
- **A test suite that leaves the email queue open stops Jest exiting.** `app` pulls in BullMQ, which holds its own Redis connection. Teardown must close `emailQueue`, `queueConnection`, the shared `redis` and disconnect Prisma — `marks.test.ts` is the pattern; `superAdmin.test.ts` matched it only after the whole suite needed `--forceExit` to quit.
- New migrations: `user_suspension`, `restrict_public_schema_access`, `password_reset_requests`. `tempPassword` moved to `modules/shared` — it was never student-specific and the lecturer module already reached across for it.


**Course visibility COMPLETE as of 2026-08-22 (uncommitted).** **120 tests / 16 suites green**, tsc + lint clean. Students saw every course their department had ever run, forever — drafts included. Plan in `PSEMS_Course_Visibility_Plan.md`. One migration (`course_batches_state_and_join_requests`), hand-written because `batch` is NOT NULL on two tables that already held rows.

- **Discovery is by batch, not department.** `Student.batch` and `CourseInstance.batch` are both **required**, trimmed and upper-cased through one `normalizeBatch`. `listStudentCpis` now matches on department **and** batch, plus everything the student joined and anything they were approved to join late. Matching on department alone was the whole bug.
- **Batch, not year of study.** A module can cross a year boundary — the Data Management Project runs semester 6 into semester 7 — so a course tagged "year 3" stops matching its own students in September. `Student.year` is also written once at provisioning and read by nothing, so it would need bumping by hand every year. A batch is fixed for life. `Student.year` stays, still unread; removing it would be a migration for no gain.
- **No semester field and no enrolment table.** Every active course for a batch belongs to that batch whichever semester it runs in, and a student is on a course because their batch matches it. The match is computed live rather than snapshotted, which is exactly why the roster exists.
- **`CourseStatus`** — `DRAFT | ACTIVE | ARCHIVED`. New courses start as drafts, so one can be set up without students watching; archiving keeps a finished course readable to the students who took it and hides it from everyone else. **The migration archived every existing course** — all test data. Drafts are hidden from `GET /courses/open` too: a course still being set up should not collect supervisor requests.
- **Required, not optional.** An optional batch would mean a course with none falls back to department-wide — this exact bug, quietly reinstated. Required turns a mistake into a loud failure instead: the course cannot be created, and the roster reads zero.
- **`CourseJoinRequest` — the repeat case.** A student below the pass mark may **ask** to take the module with a later batch; the coordinator decides. Never automatic. One table, not a request plus a grant: **an approved request is the access**, and discovery reads it directly. `GET /courses/other-batches` lets them name a course they cannot see — name, batch and project type only, the same boundary `listOpenCpis` draws for lecturers.
- **An approved request also lifts the phase gate**, in `requirePhase` itself, scoped to `LATE_JOINER_PHASES` (`STUDENT_REGISTRATION` and `PROJECT_SELECTION`). Without it the approval is empty: a repeat is decided **after** the previous course ends and its marks are out, by which time the new course has moved past both. Submission and evaluation windows still apply to them exactly as to everyone else.
- **`getCourseRoster`** — everyone the course is for, and what each is doing: in a group, working alone, or **not started**. The admin uploads the batch so the system knew all of them; the coordinator could only ever see the groups that happened to exist, and a student who never started was invisible to allocation, sessions and marks alike. A roster of **zero** is also how a mistyped batch is caught.
- **`passMarkPercent`** on the policy. The CA sheet flags and counts students below it. **Coordinator-facing only, permanently** — being repeated is a formal decision the department makes and communicates, not a verdict PSEMS announces from a number. No flag exists to turn this on for students.
- **`targetGroupSize`** on the policy, and **`allowIndividualParticipation` now defaults to true**. A batch rarely divides evenly, so the student left over must still be able to proceed, and a group over or under the target is flagged on the roster rather than refused — the same warn-not-block rule the scheduling conflicts and late submissions already follow.
- **`PUT /evaluations/stage-weights`** takes every stage's weight at once and validates the sum. Weights were locked out of the patch path once submissions existed, so on a two-semester module the first semester's report upload froze the credit split. Refused once a `FinalMark` exists, matching Wave 1's rule that aggregation, not approval, is the point of no return.
- **The student CSV gained `batch`** (required) — header is now `email,fullName,studentIndex,registrationNumber,batch,department`. (`year` dropped and `studentId` renamed to `studentIndex` on 2026-08-23; see the entry at the top.)
- `visibility.test.ts` covers all of it: batch filtering, drafts, archived courses staying visible to those who joined, case-and-space normalising, request → approve → access, pending and rejected granting nothing, an approved student starting after registration closed while a normal student cannot, and the roster including a late joiner.

**The roster tests were not isolated, and only a parallel run showed it.** `getCourseRoster` looks students up by **batch and department**, but the shared harness isolates suites by **email prefix only** — batch and department default to the same values in all 15 suites. Run with `--runInBand` they passed; run by `npm test` (which is plain `jest`, so parallel — as CI runs it) the roster counted every other suite's students and four assertions failed. `visibility.test.ts` now uses its own `VIS22ENG` / `VIS21ENG` batches and a `CE-VIS` department, and looks rows up by index number rather than position. **`MakeUserOptions.batch` carries a warning**, because any future test that queries by batch or department will hit the same thing.

- **The mark sheet never returned the pass mark.** Two of four edits to `getMarkSheet` had silently no-opped — `str.replace` does nothing when it does not match, and the file had moved on since. `belowPassMark` was therefore false for everyone and `passMarkPercent` was absent, while the frontend types happily declared both. Nothing across the wire is typechecked, so only the test caught it.

**Existing tests needed fixture updates, and two assertions changed on purpose:** working alone on a group course is now allowed by default (the test now also covers a coordinator turning it off), and a draft course is no longer discoverable by lecturers (the test now asserts that before publishing).

**Role-derived profiles COMPLETE as of 2026-08-16 (uncommitted).** **102 tests / 15 suites green**, tsc + lint clean. No schema change.

- **`getProfile` now returns `ownProjects` beside `supervisedProjects`.** `supervisedProjects` reads the `Lecturer` row, so it was always `[]` for a student — which is why the profile page could only ever show a student an empty "Projects supervised" tab. `ownProjects` derives a student’s projects from their accepted group memberships’ allocations, **stored nowhere**, the same rule as the supervised list, and names the supervisor rather than the group-mates.

**Reachability pass COMPLETE as of 2026-08-16 (uncommitted).** A sweep of all 121 routes against every frontend call found nine features that were built, tested and reachable from no screen — and three that were broken end to end. **101 tests / 15 suites green**, tsc + lint clean.

- **Walk-in marking was unreachable, not just unwired.** `listSessions` threw 403 to any lecturer who held no seat, was not a supervisor and was not a CPI evaluator — so a lecturer walking into an open FYP demo could not list the sessions, could not find a session id, and therefore could never reach `POST /panel/join`. `openToAll` and the join endpoint had both existed since Wave 1 with no way in. `listSessions` now also returns sessions whose stage carries an `openToAll` panel rule, **to approved lecturers only, and only those sessions** — widening visibility must not turn a timetable into a public document. Two tests: an outsider finds and joins an open stage (idempotently), and a course with no open stage still 403s.
- **Allocations could be locked but never unlocked.** `overrideAllocation` 409s once `allocationsFinalizedAt` is set, and nothing cleared it — so a supervisor going on leave in week 10 could not be replaced at all, against an explicit requirement. `POST /allocations/reopen` takes a mandatory reason and is **refused once any `FinalMark` exists for the course**, mirroring the session reopen rule: finalizing is not the point of no return, aggregation is.
- **The allocation phase gate moved into the service**, exactly as scheduling's did in Wave 3 and for the same reason. `PROJECT_REGISTRATION` opens pairing and no longer closes it; only `generate` (seeding from selections) stays strictly inside the phase. A route-level gate made a legitimate late change a hard 403 long after the only permitted moment had passed. The finalize lock is the real protection, not the calendar.
- **Nothing else needed backend work.** The remaining gaps were all frontend — endpoints and hooks that existed with no screen. See `psems-frontend/CLAUDE.md`.
- **No TODO or FIXME exists in either repo.**

**Course settings restructure COMPLETE as of 2026-08-16 (uncommitted).** Backend half is small — one route — but it unblocked the frontend rebuild of the settings screen. **97 tests / 15 suites green**, tsc + lint clean.

- **`POST /courses/:cpiId/preset` `{mode}`** applies either preset by name. `presetFor()` had always seeded a policy at creation, but there was **no way to re-apply one afterwards and only `COORDINATOR_MANAGED` had an endpoint** — a coordinator who edited their way into a corner had to undo it setting by setting. `applyCoordinatorManagedPreset` is now a one-line delegate and its old route is kept, so nothing that called it breaks.

Re-applying a preset that silently reverted unrelated work would make the button unusable.

**Restructure Wave 4 COMPLETE as of 2026-08-16 (uncommitted).** Per-student marks, grade bands, per-stage publishing and the CA sheet. One migration (`student_marks_grades_and_publication`), written by hand so the 3 courses that had already published kept that fact — each became a course-wide `mark_publications` row before `marks_published_at` was dropped. **This is the last wave; the restructure is done.**

- **`StudentMark`** (unique per student and stage) sits alongside `FinalMark`. GROUP criteria give every member the same share of the stage; INDIVIDUAL criteria give each member their own. The two halves are stored separately (`groupComponentPercent` / `individualComponentPercent`) so a student can see which part of a mark was the group's work.
- **The group's own figure is the average of its members'.** With only GROUP criteria every member scores the same, so this is identical to what the group mark has always been — existing courses see no change.
- **A criterion nobody scored counts as zero**, so the mark shows the shortfall rather than hiding it. Re-sharing the missing weight over the scored criteria would award a mark for work nobody assessed. Readiness tells the reviewer how many panelists have finished before they close scoring, so this only arises when they close short — which is allowed and audit-logged.
- **`GradeBand`** per course, stored highest first so a lookup is "the first band the mark reaches". Only applied when `policy.gradingEnabled`; a CA-only course has no bands and every grade is null.
- **`MarkPublication` replaces `CourseInstance.marksPublishedAt`.** Marks and comments are separate switches, set per stage or for the whole course, **and either can be turned off again** — the old timestamp could be set once and never cleared. A stage's own row wins; otherwise the course-wide row applies; otherwise nothing is visible. The course-wide row is kept unique by a **partial index**, because Postgres treats null stage ids as distinct.
- **A student pre-publish now gets 200, not 403.** Per-stage publishing means "published" is no longer one yes/no — a 403 cannot say "the proposal is out but the demo is not". `getMarks` returns the visible stages plus `pendingStages` naming the rest. **This is a deliberate breaking change to the Week 8 contract**; the frontend no longer treats 403 as an empty state.
- **A student sees only their own breakdown**, never a group-mate's individual marks, even though both hang off the same group.
- **The CA sheet** (`GET /marks/sheet`, coordinator only) is one row per student with a weight row summing to 1.00, one column per stage, a total, and **zero totals flagged rather than dropped** — a zero usually means someone was never scored. Names are stored as one field, so the sheet takes the last word as the surname and initials from the rest; the full name is sent too.

All advisory - never a block.

A timetable is edited *most* after the window shuts (someone drops out, a room changes), and the route gate made that a hard 403. Bulk `PUT /sessions/schedule` lays out a block in one call.
